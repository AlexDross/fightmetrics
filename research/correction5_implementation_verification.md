## What was wrong

`update_fighters.py` read the roster with two independently written regexes:

```python
re.finditer(r"\{n:'([^']+)'[^}]+\}", js_content)   # identity
re.search(r"w:'([^']*)'", entry_str)               # division
```

`[^']` cannot cross the backslash of an escaped apostrophe, so both stopped one
character early. `n:'Sean O\'Malley'` decoded to `Sean O\`, which matched no
CSV-derived update key, so nine fighters silently stopped receiving record and
aggregate updates. `w:'Women\'s Flyweight'` decoded to `Women\`, which shipped
as the weight class on 1,849 `fightHistory` entries.

Repairing only the identity parser would have been a regression, not a fix:
`ufc_fight_details.csv` is `EVENT,BOUT,URL`, so every fight record carries
`wc: ''` and the recomputed `tb` collapses to an event-name heuristic matching
one card in the entire feed. Sean O'Malley's stored `tb: 4` would have gone to
`0` the moment he re-entered the update path.

## What changed

**`js_roster_parser.py` (new).** One tokenizer for the generated JS modules,
import-safe: it reads no file, loads no feed and runs no updater code, so the
grammar is unit-testable without pandas or the CSVs. A single quoted-string
scanner serves identity, division and every other field; objects are split by
balanced-brace tokenizing with strings and comments consumed by that same
scanner. Each object's raw source text and per-field byte offsets are kept, so
fields are patched by targeted splice — the roster is never deserialised and
re-serialised. No `eval`, no `exec`, no Node, no permissive JS evaluator.

Fail-closed: an unparseable object, text the tokenizer did not claim, a
duplicate identity, or two different escapes decoding to the same identity all
raise `JsParseError`.

**`update_fighters.py`.** Reads the roster through `parse_roster`; `existing`
and `wc_lookup` are both built from that one parse. Its four ad-hoc parse
helpers and its `patch_field`/`js_escape`/`fmt` regex writers were replaced by
the shared module. `tb` was removed from `STAT_FIELDS`, and the misleading
recomputed `tb` was removed from `compute_stat_updates` since nothing consumes
it. A `PRESERVED_FIELDS = ('tb',)` guard holds regardless of what `STAT_FIELDS`
later contains. Before the roster is written, the run asserts that every
original identity survives (only explicitly seeded newcomers may be added), that
each entry's field set changed only by the `_NEW_FIELDS` backfill, and that
every field outside `PATCHED_FIELDS` is byte-identical to what was read.

### Second instance of the same defect, found by the new parser

`src/prospectsData.js` is hand-maintained and carries `//` section headers, one
reading `(Women's BW, Prelims)`. The old scanner had no notion of comments, so
that apostrophe opened a string and brace parity was lost for the rest of the
file: **`load_prospect_fallbacks` saw 4 of the 12 prospect entries.** The new
tokenizer skips comments and sees all 12.

This is the same apostrophe defect in the same read path, so it is repaired
here rather than deferred. It changed **no generated byte** in this run —
`prospect_fallbacks` only feeds new-fighter seeding, and this run seeded zero
new fighters — which the artifact hashes below confirm.

### The prospect path is fail-closed too

Review caught that the first cut of this change widened the prospect path
without giving it the roster path's guarantees. Its loader still extracted,
split and re-parsed objects itself, so four ways to lose an entry survived in
the very code that had just gained eight of them:

| Hole | Now |
|---|---|
| `JsParseError` from `extract_array_body` caught and turned into `{}` | no `except` anywhere in the loader |
| object with no decoded `n` skipped by `if not name: continue` | `parse_roster` raises |
| duplicate decoded names overwriting each other in the result dict | `parse_roster` raises, and the dict size is asserted against the object count |
| `split_top_level_objects` skipping `parse_roster`'s residue and identity checks | there is no split path left |

`parse_prospect_fallbacks(content)` in `js_roster_parser` is now the only way
in. It is import-safe, calls `parse_roster(content, '_P')` and builds each
fallback from the `RosterEntry.fields` that call already decoded — it does not
extract, split or re-parse anything itself.

The loose by-key helpers that made a second, laxer read path easy to reach for
(`parse_js_string_field`, `parse_js_number_field`, `parse_js_nullable_field`,
`split_top_level_objects`) were **deleted**. Nothing else in the repository used
them. Their replacements, `field_string(fields, key)` and
`field_number(fields, key)`, take an already-parsed field map rather than raw
text, so no caller can decode a field with a grammar the rest of the run did not
use. A test asserts those four names stay gone.

**Absent-file policy, decided explicitly.** `src/prospectsData.js` is tracked,
so every checkout and CI run has it. Its absence remains *optional* — a stripped
tree simply seeds without physical-attribute fallbacks, the long-standing
behaviour — but that is the **only** path to `{}`, guarded by
`not os.path.exists(PROSPECT_PATH)` and nothing else, and the run prints a
warning when it happens. A file that **exists but does not parse aborts the
updater**. Tests read this from the AST rather than the source text, because the
function's docstring describes the swallowing it must never do again.

This change is behaviour-preserving for the shipped file — all 12 entries
resolved before and after — and the artifact hashes below were re-verified from
the pristine baseline after it.

## What this change does not claim

`fightHistory.wc` still falls back to the fighter's **current roster division**,
because `fight['wc']` is always `''`. The 59 `Unknown → division` repairs are
that fallback finally resolving for the nine fighters, not an assertion that
those bouts were contested at that weight. A fighter who changed divisions still
shows their present division across their whole history.

Authoritative historical bout division and title provenance — reading raw
`WEIGHTCLASS` from `ufc_fight_results.csv` before `clean_wc` strips
`UFC`/`Title`/`Bout`/`Interim` — is **correction 6**, deliberately untouched
here. `build_new_fighter_entry`'s `tb` expression for newly seeded fighters is
also left exactly as it was.

## Tests

`test_js_roster_parser.py` (35 tests) and `test_correction5_identity.py`
(26 tests) are stdlib-only, read no feed, and are wired into both `ci.yml` and
`update-fighters.yml`. `test_correction5_full_run.py` (11 tests) pins the
one-time scale figures and is gated behind `CORRECTION5_BASELINE_TREE`, because
every later scheduled refresh legitimately moves both sides of that comparison.

Prospect-path coverage specifically: the shipped file resolves **exactly 12**
entries (not "greater than zero" — a number quietly too small is the whole
failure mode); the loader's identities equal `parse_roster(..., '_P').names`;
the `(Women's BW, Prelims)` comment is still supported; and missing identity,
duplicate identity, unescaping collision, malformed object, missing export and
stray unclaimed text each hard-fail, with a table-driven test asserting that no
input can silently shrink the result.

```bash

CORRECTION5_BASELINE_TREE=/tmp/c5-base \
```
