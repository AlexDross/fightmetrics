staleness and `rankHistory`'s March-12 cap do not touch the default V2/live betting
path.** But that is **not** the same as "doesn't matter": SOS **does** affect V1's

and current `UFC_RANKINGS` are independent artifacts on their own manual cadences
and remain **out of scope for a Greco-pipeline repair** — but `rankHistory`'s
March-12 cap should still be refreshed on its own track because it degrades V1
whenever V1 is inspected.

## Part B — The `daysSinceLast` run-date recompute: same code, distinct consequence

**Finding: this is the SAME code already inventoried in
`research/daysSinceLast_live_audit.md`, but a DISTINCT, previously-undocumented
consequence of it.**

- **Same code:** `daysSinceLast_live_audit.md` Step 1 already lists
  `update_fighters.py:297,305` — `TODAY = date.today()`;
  `dsl = (TODAY - date.fromisoformat(lfd)).days` — as "a second, independent
  instance of the same [`Date.now()`-anchored] pattern." Same two lines.

- **Different consequence.** That audit analyzed the line for its **feature-value
  distortion** (the `dsl` fallback feeding a wrong layoff/`modern_form` value for
  history-less fighters). It did **not** connect the second-order effect the
  second review flagged: because `dsl` is recomputed against `date.today()` on
  **every** run and written unconditionally, **every scheduled run mutates
  `fightersData.js` even when zero new fight data arrived** — which manufactures a
  non-empty git diff, so the workflow's commit step fires and the run reports
  success.

- **Evidence for the masking mechanism (file/line):**
  - `update_fighters.py:305` — `dsl` recomputed from `TODAY` for every fighter in
    `record_updates`.
  - `update_fighters.py:498` — `dsl` is in `RECORD_FIELDS`, so
    `update_fighters.py:513` `patch_field(entry_str, 'dsl', u['dsl'])` rewrites it
    into each entry unconditionally.
  - `update_fighters.py:549` — `fightersData.js` is written every run regardless
    of whether any event is new.
  - Result: with a fixed roster and a frozen `lfd`, each daily run bumps every
    fighter's `dsl` by the elapsed days → `git diff --staged` on
    `src/fightersData.js` is non-empty → `.github/workflows/update-fighters.yml`
    commit step runs `git commit … && git push` → "✅ Pushed updated fighter
    data" → Vercel redeploy. The pipeline **looks** healthy while ingesting
    nothing. This is precisely why ~59 days of no-new-events went unnoticed.

  **Classification:** not a new code instance — a **distinct failure mode of the
  documented line**. The existing audit covers "wrong feature value"; this covers
  "false signal of pipeline health." Both trace to `update_fighters.py:297,305`.
  Recommend cross-linking the two in `daysSinceLast_live_audit.md` on the next
  pass (not done here — report-only).

## Part C — Three-target access proof (isolated scratchpad, NOT a full scrape)

**Method.** In a fresh scratchpad clone of `Greco1899/scrape_ufc_stats`, monkey-
patched `LIB.get_soup` with a proof-of-work-solving `requests.Session`: on
receiving the challenge it extracts the `nonce` + zero-count, brute-forces `n`
where `sha256(f"{nonce}:{n}")` has the required leading zeros (target = 2 hex
zeros, ~256 hashes), POSTs `{nonce, n}` to `/__c`, receives a 7-day `_fmc` cookie,
retries. The cookie persists in the session, so **only the first request solves;
all subsequent fetches reuse the cookie.** Then ran Greco's **own unmodified
parser functions** on each page type.

**Results — all three page types returned real, parseable content past the
challenge, and Greco's parsers handled them correctly:**

| # | Target | Greco function | Result |
|---|---|---|---|
| 1 | Events-listing (`/statistics/events/completed?page=all`) | `parse_event_details` | **780 events** parsed (vs 774 in stale CSV); real page, not challenge |
| 2 | Event-details (`…/event-details/1e75e6c9de99fa76` — UFC Fight Night: **Song vs. Figueiredo**, the "Yadong vs. Figueiredo" from upstream issue #34) | `parse_fight_details` | title parsed; **13 bouts** parsed (top: "Song Yadong vs. Deiveson Figueiredo") |
| 3 | Fight-details (`…/fight-details/423f32dd018ac218` — Song Yadong vs. Deiveson Figueiredo) | `parse_organise_fight_results_and_stats` | result row parsed (`OUTCOME W/L, METHOD Submission, ROUND 2`) + per-round stat rows (KD, SIG.STR., TD, …) |

**Total network cost of the proof: 1 PoW solve + one card's worth of page fetches
(seconds).** No full-historical scrape was run, in scratchpad or anywhere.

**New completed events behind the wall (May 16 → today), for scope:** Song vs.
Figueiredo (Jun 6), Muhammad vs. Bonfim (Jun 14), UFC Freedom 250 (Jun 20), Kape
vs. Horiguchi (Jun 27), Fiziev vs. Torres (Jul 11) — **5 missed completed cards**,
new max completed date **~2026-07-11**; plus upcoming UFC 329: McGregor vs.
Holloway 2 (Jul 18). (ufcstats lists the next card at the top of the completed

## Part D — Fail-closed freshness gate (design only — NOT implemented)

**Goal:** make the workflow **fail loudly** when the incoming data is implausibly
stale or hasn't grown, instead of silently committing `dsl`-only churn (Part B).

**Where it lives:** a new step in `.github/workflows/update-fighters.yml`, placed
**after** "Download Greco1899 UFC stats CSVs" and **before** "Run
update_fighters.py". Implemented as a small standalone script, e.g.
`scripts/check_data_freshness.py`, invoked with `python scripts/check_data_freshness.py`
so a non-zero exit fails the job (default `set -e` behavior of a run step).

**Inputs it reads:**
- The freshly downloaded `ufc_event_details.csv` (present in the runner even though
  it's gitignored in the repo — it has the `DATE` column).
- `ufc_fight_results.csv` (row count) — this one *is* git-tracked, so its committed
  version is the prior-run baseline.
- The persisted anchor `src/sourceManifest.js` → `maxObservedEventDate`
  (currently `"2026-05-16"`) — the last verified max event date. (Note:
  `ufc_event_details.csv` itself is gitignored, so the prior max date must come
  from this persisted manifest, not from a committed prior CSV.)

**Checks (fail-closed — any failure exits non-zero and stops the run):**

1. **Absolute staleness.** Compute `max_event_date` from the incoming
   `ufc_event_details.csv`. If `run_date_utc - max_event_date > MAX_STALE_DAYS`
   → **FAIL**. Recommend `MAX_STALE_DAYS = 14` (UFC runs ~weekly; genuine gaps of
   up to ~2 weeks happen around holiday breaks, so 14 avoids false alarms while
   still catching the current 59-day gap immediately; make it an env var so it can
   be tuned). The second review's ~10 is also defensible but risks tripping on a
   normal 2-week lull — 14 is the safer default.

2. **No-advance vs. persisted anchor.** Parse `maxObservedEventDate` from
   `sourceManifest.js`. If incoming `max_event_date <= stored maxObservedEventDate`
   → **FAIL** ("max event date has not advanced since last verified run"). This is
   the direct catch for "the scrape returned nothing new."

3. **Count non-increase.** Compare incoming `ufc_event_details.csv` event count and
   `ufc_fight_results.csv` row count against the git-tracked committed
   `ufc_fight_results.csv` (baseline). If neither increased → **FAIL** ("event and
   fight counts did not grow"). Belt-and-suspenders with #2 in case a date is
   miscoded but rows still didn't grow.

4. **Challenge-page guard (cheap + high-value).** If the incoming
   `ufc_event_details.csv` has drastically fewer rows than the committed baseline
   (e.g. `< 0.9 ×` prior row count, or 0 rows) → **FAIL**. This catches the exact
   failure we hit: a scraper that silently produced an empty/near-empty file after
   receiving the challenge page. Prevents a future path where the workflow *does*
   run the scraper directly and overwrites good CSVs with challenge-page garbage.

**Pseudocode:**

```python
# scripts/check_data_freshness.py  (DESIGN ONLY — not added in this task)
import csv, re, sys, os
from datetime import date, datetime

MAX_STALE_DAYS = int(os.environ.get("MAX_STALE_DAYS", "14"))

def max_event_date(path):
    ds = []
    for r in csv.DictReader(open(path)):
        try: ds.append(datetime.strptime(r["DATE"].strip(), "%B %d, %Y").date())
        except Exception: pass
    return max(ds), len(ds)

incoming_max, incoming_events = max_event_date("ufc_event_details.csv")
prior_max = datetime.strptime(
    re.search(r'"maxObservedEventDate":\s*"([\d-]+)"',
              open("src/sourceManifest.js").read()).group(1), "%Y-%m-%d").date()

# baseline from the git-tracked committed CSV (HEAD version), fetched in the step
prior_results_rows = int(os.environ["PRIOR_RESULTS_ROWS"])   # e.g. `git show HEAD:ufc_fight_results.csv | wc -l`
incoming_results_rows = sum(1 for _ in open("ufc_fight_results.csv")) - 1

fail = []
if (date.today() - incoming_max).days > MAX_STALE_DAYS:
    fail.append(f"stale: max event {incoming_max} is >{MAX_STALE_DAYS}d before today")
if incoming_max <= prior_max:
    fail.append(f"no-advance: incoming max {incoming_max} <= stored {prior_max}")
if incoming_results_rows <= prior_results_rows:
    fail.append(f"no-growth: results rows {incoming_results_rows} <= prior {prior_results_rows}")
if incoming_events < 0.9 * 774:  # or < prior event count
    fail.append(f"suspicious-shrink: only {incoming_events} events parsed")

if fail:
    print("FRESHNESS GATE FAILED:\n  " + "\n  ".join(fail)); sys.exit(1)
print(f"OK: max event {incoming_max}, {incoming_events} events, {incoming_results_rows} result rows")
```

**Interaction with the `dsl` masking:** the gate must run **before**
`update_fighters.py`, so it evaluates the *raw incoming CSV*, not the
`dsl`-mutated `fightersData.js`. That's what makes it immune to the Part-B masking
— it never looks at the artifact whose daily churn creates the false success.

## Implementation (2026-07-15)

Follow-up task shipped **only the zero-prediction-risk parts** of this report. The
`dsl` storage/derivation change (old Part 3) was **deliberately deferred**, not
forgotten — `dsl` is consumed as a live V2 model fallback (`App.js:802`), so
changing its representation carries prediction risk that must be isolated and
tested on its own. `update_fighters.py`'s `dsl` calculation was **not touched**.

**1. Fail-closed freshness gate — `scripts/check_data_freshness.py` (new).**
Runs in `update-fighters.yml` after the CSV download, before
`update_fighters.py`/`regen_elo.py`. Reads the freshly downloaded
`ufc_event_details.csv` (max event date + event count) and `ufc_fight_results.csv`
(row count), and compares against the baseline in `src/sourceManifest.js`
(`freshnessBaseline` block) — **no counts are hardcoded in the gate**.

- **FAIL (exit 1, stops the run):** CSV missing/unparseable or missing a required
  column; incoming max event date < baseline; event or result count decreases vs.
  baseline; **or** newest event is more than **14 days** older than the run date
  (regardless of internal consistency).
- **PASS, NO NEW DATA (exit 0, logged distinctly):** max date and counts unchanged
  and within the 14-day window.
- **PASS, NEW DATA (exit 0):** max date advances (or counts grow) with all
  structural checks green. Emits `new_data=true` for the manifest-regen step.

  **Threshold = 14 days, reasoning:** UFC runs ~weekly, so the newest event is
  normally ≤7 days old on a Mon/Thu run; genuine lulls of up to ~2 weeks occur
  (Greco's own history has a 2026-02-08 → 2026-02-22 gap). 14 tolerates the
  longest-normal gap without a false FAIL while still catching a truly stuck
  pipeline immediately; 10 would risk tripping a legitimate 2-week gap. A false
  FAIL is a loud, re-runnable workflow failure — never silent bad data.

  **Historical validation (against real `Greco1899` CSV git history):**

  | Case | Baseline → incoming | ref date | Verdict | Exit |
  |---|---|---|---|---|
  | New data | May 09 / 773 / 8688 → May 16 / 774 / 8701 | 2026-05-17 | PASS new-data | 0 |
  | **No new data** (counts unchanged) | May 16 / 774 / 8701 → same | 2026-05-20 | **PASS no-new-data** | 0 |
  | Regression | 774 / 8701 → 773 / 8688 | 2026-05-17 | FAIL (regression ×3) | 1 |
  | Stale (real current stuck state) | May 16 → May 16 | 2026-07-14 | FAIL (59d stale) | 1 |
  | Boundary 14d | May 16 → May 16 | 2026-05-30 | PASS no-new-data | 0 |
  | Boundary 15d | May 16 → May 16 | 2026-05-31 | FAIL (15d stale) | 1 |
  | Structural (no DATE col) | corrupt event CSV | 2026-05-17 | FAIL (structural) | 1 |

  The **no-new-data case PASSes, not FAILs** (revert-threshold requirement met).
  Note: with this gate live, the **current stuck-at-2026-05-16 data will make the
  scheduled run FAIL immediately** — that is the intended fail-closed behavior, not
  a regression; it clears automatically once upstream data advances past the
  14-day window.

**2. Manifest-regeneration wiring (was missing).** `generate_source_manifest.py`
now emits a structured `freshnessBaseline` (`maxObservedEventDate`, `eventCount`,
`resultRowCount`) — previously the counts existed only inside a prose
`verificationMethod` string. `update-fighters.yml` gained a
`Regenerate source manifest (on new data)` step (`if: new_data == 'true'`) after
`regen_elo.py`, and `src/sourceManifest.js` was added to the commit's `git add`
set — so on every real refresh the baseline advances instead of being frozen at
whatever it was last hand-generated.

**Out-of-scope / unchanged (confirmed):** `update_fighters.py` `dsl` logic; all V2
coefficients/`W_OD`/`PLATT_*`/`SCALES`; `eloModule.js`, `cardioModule.js`,
`backtest_combo_v2.py`. On no-new-data days the existing ingest/commit behavior
(including the `dsl` daily churn from Part B) is intentionally left as-is — the
gate now catches the *dangerous* stuck case (stale beyond threshold) loudly, while
the benign within-window churn is left for the deferred `dsl` task.
